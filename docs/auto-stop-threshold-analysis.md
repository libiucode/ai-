## 0.1 修订说明（重要）

本文档初版把 `2920b432` 当作「真实直播样本」来推算阈值，**这是错的**。经独立复核（`scripts/analyze-boundary.cjs`，只读），确认三点：

| 初版写法 | 实测事实 |
|---|---|
| `2920b432` 是 CCTV-13 **新闻**直播 | ⚠️ **半对**。流地址标签确实是 CCTV-13（`http://74.91.26.218:82/live/cctv13hd.m3u8`），**但那段时隙播的是降糖保健品广告口播**（「跟丹参配伍，能提取出高倍浓缩的化糖肽…」），不是新闻。**「流标签」不等于「内容性质」** |
| 真实直播最长静默 **49.8 秒** | ❌ 49.8s 是 **124.4s → 174.2s 的音源切换间隙**（干净音源已停、TTS 未起，该区间无任何音源）。**干净窗口内最长静默 0.4 秒**（n=1） |
| 真实直播样本 **1 场**（743 秒） | ❌ **干净样本为 0 场完整直播**。该会话 742s 里只有 **124.8s** 是干净广告口播，之后是 49.8s 无源间隙 + 约 568s 带货 TTS |

**因此本文档 §2「最长 49.8 秒」与 §3.2「12 倍安全边际」的推算基础作废**，已在对应位置改正。**§4（设备故障信号优先）与 §3.3（三步流程）不受影响，仍然成立。**

## 0. 结论先行

| 问题 | 结论 |
|---|---|
| `silent`（内容静音）能否直接用于自动结束？ | **不能单独用** |
| 用什么信号自动结束才安全？ | **设备故障级信号（ended / muted / deviceLost / stalled）应立即结束**；`silent` 只能作为「升级警告」 |
| 若一定要对 `silent` 设阈值，建议多少？ | **暂无数据支撑具体数值**（见 §3.2）。可先用 **10 分钟**作为工程兜底，但必须配「先警告、后结束、记录原因」三步 |
| 实测最长自然静默 | **干净样本 0.4 秒**（n=1）；**49.8 秒那个极值来自音源切换间隙，不可用** |

**核心发现：干净直播素材里的自然静默极短（0.4 秒），因此「无音频自动结束」在真实直播场景下几乎不会触发。**
它的实际价值只在两类场景：**失败会话**（ASR 连着但采不到可用音频，空转接近 100%）和**用户忘关会话**。

## 3. 阈值建议

### 3.1 我原先的建议是错的（两次）

我在上一轮**没有数据**时建议过 30 分钟，理由是「直播间正常静默（BGM 段、商品特写）常超 5 分钟」。**数据显示这个担心被高估了。**

但随后初版又犯了反向错误——**把 `2920b432` 的音源切换间隙当成「真实直播最长静默」**，据此说「10 分钟有 12 倍边际」。

修正后的事实：

- **干净真实直播样本最长静默 0.4 秒**（`b217299a`，n=1 段）
- 干净长跑样本 0.8 秒（`f941151f`）
- 超 60 秒的静默段：**仅 1 个，且是音源切换间隙，不是静默**

### 3.2 建议阈值：**暂无实测支撑，先用 10 分钟兜底**

| 阈值 | 评价 |
|---|---|
| 60 秒 | **太激进**。虽然干净样本最长仅 0.8s，但样本量太小（2 场），且带货 BGM 段未被观察到 |
| 3 分钟 | 偏激进，边际仍有风险 |
| **10 分钟** | **工程兜底值，不是数据结论**。它相对干净样本是 750 倍安全边际，**但也正因如此，它几乎永远不会触发**——见 §3.3 |
| 30 分钟 | 安全但止损太慢，浪费额度 |

> ~~10 分钟：相对实测最长静默有 **12 倍**安全边际~~ ← **作废**。12 倍是拿 49.8s（音源切换间隙）当基准算出来的，基准错误。
> 按 0.4s 算边际是 **1500 倍**，但**这个数字恰恰证明该机制在干净直播里不会触发**，不能说成「安全」。

**为什么不是「刚好 60 秒 × N」**：实测数据只覆盖了极少会话和有限内容类型，且**没有任何一场干净的带货直播**。综艺、带货直播的静默模式可能完全不同（如长时间商品展示）。**在补采到干净带货样本之前，任何具体数值都是猜。**

### 3.2.1 本案的真实收益上限：几毛钱量级

| 场景 | 会不会触发 10 分钟阈值 | 说明 |
|---|---|---|
| 干净真实直播 | ❌ 不会（最长 0.8s） | 机制形同不存在 |
| 带货直播（未测） | ？ | 无样本 |
| **失败会话**（`a83d2607` 518 区间/0 片段、`e0624009` 1793/0） | ✅ **会** | 连着 ASR 但产不出可用音频，**这才是真正值得止损的场景** |
| **用户忘关会话** | ✅ 会 | 止损价值最大 |
| **残留会话**（`b54b7436` 622 分钟） | ✅ 会 | 但已由 `closeStaleSessions` 覆盖 |

**结论：把「无音频自动结束」当作失败会话/忘关的兜底，不要指望它省静默额度。**
（补充：全库 8 个有音频会话的空转合计浪费约 **0.63 元**；单个残留会话 622 分钟约 **33 元**——相差 52 倍。**止损大头在残留，不在静默。**）

### 3.3 但阈值不是关键，流程才是

**绝不应该静默地自动结束会话。** 建议三步：

```
① 连续 10 分钟电平为 0 且设备健康
   → UI 显著提示「已 10 分钟无音频输入，是否结束本场？」（不结束）
② 再过 5 分钟仍无输入
   → 自动结束会话
③ 结束时必须写明原因：「因长时间无音频输入自动结束」
```

**第 ③ 步最关键。** 否则用户看到一场「正常结束」的空会话，无法区分是软件故障还是自己忘关——这正是实时转写遇到的「40 条数据被污染」的成因之一。

## 4. 比阈值更重要的：优先用「设备故障」信号

`silent` 的语义是「**设备正常、链路正常，只是没声音**」——这正是**不该自动结束**的情况（可能是合法静默，也可能是用户暂时离开）。

而**设备故障级信号一旦出现，采集已不可能自行恢复**，继续挂着 100% 是浪费额度：

| 信号 | 判据 | 建议动作 |
|---|---|---|
| `ended` | 轨道 readyState = ended | **立即结束** |
| `muted` | muted 持续 ≥ 6s | **立即结束** |
| `deviceLost` | 设备从列表消失 | **立即结束** |
| **`stalled`** | **`AudioContext.state` = suspended/interrupted**（**已改，原判据「回调停更 ≥3s」已废弃**——静默时回调本来就会变慢，该信号与 `silent` 无法区分） | **立即结束** |
| `silent` | 仅电平为 0，设备健康 | 警告 → 10 分钟后结束（§3.3） |

**这是本次评估最重要的结论**：自动结束的**主要依据应该是设备故障，而不是静音时长**。静音时长阈值只是兜底。

> **`stalled` 判据变更说明**：原判据（音频回调停更 ≥ 3s）会在正常长静默时误报，**误判导致的真实中断比漏判更严重**。已改为读 `AudioContext.state`，`running` 时静默多久都不判故障。详见 `docs/lessons-false-positive-outage.md`。**该新判据目前仅有单测覆盖，真实行为未实测。**

配套：采集侧已实现四级判据并通过 `onDeviceLost` 回调上报（`renderer/capture/audioCapture.ts`，`capture-health.test.ts` **25/25**）。

## 5. 数据局限（必须标注）

| 局限 | 影响 |
|---|---|
| **干净的真实直播样本为 0 场完整的带货直播**；仅 `b217299a`（CCTV-1 电视剧 245s）与 `f941151f`（CCTV-1，82s）两场干净电视素材 | **阈值无实测支撑**；带货直播的静默模式完全未知 |
| `2920b432` 是混合会话（广告口播 + 无源间隙 + 带货 TTS） | 初版错误引用它导致「49.8s 极值」与「12 倍边际」两个错误结论，已作废 |
| 多数字符串来自 TTS 测试音 | TTS 静默模式不代表真实直播，已单独区分统计 |
| 会话时长普遍偏短（多数 < 300 秒） | **无法观察到「小时级」的静默行为**；10 分钟阈值的安全性对长会话是外推 |
| 部分会话语音区间数异常大（`5970a6d6` 2225 条覆盖 551s / `a83d2607` 518 条 0 片段） | 前者是 TTS 特征，后者是失败会话；均不代表真实直播 |

**结论强度**：**本文档的阈值建议已从「有数据支撑的工程建议」降级为「工程兜底值，无实测支撑」**。真实上线前必须补采**干净的带货直播素材**（韩束官方旗舰店等），否则不要宣称任何安全性边际。

**引用纪律**：今后任何引用 `2920b432` 的统计，必须同时标注 **所属时间区间**（干净口播 0~124.8s / 无源间隙 124.4~174.2s / 带货 TTS 174.2s 后）。只写 sessionId 的引用一律视为无效。全局画像见 `evidence/session-profiles.json`。
