### INC-01 实时字幕不显示（2026-10-14）

- **现象**（用户原话）：「大模型导入正常，语音输入也正常，聆听声音也有声音调整（电平条在跳），就是不显示字幕。」数据库实测 `transcript_segments` 0 条、`analysis_runs` 0 条，监控页临时字幕与稳态字幕双空白；ASR 显示「识别中」。
- **根因**：腾讯云实时 ASR WebSocket 实际句子字段为 `result.index`、`result.voice_text_str`。原实现读 `result.slice_seq`、`result.result_text`，真实响应被解析成序号 0、空文本；随后去重判断 `seq <= lastSeqSeen` 又把同一句的后续响应全部丢弃。即使只修字段，同一句的临时结果更新与最终结果仍会被丢弃（句子的 index 在临时与最终消息之间保持不变，下一句才增加）。
- **修复**：`src/main/asr/tencentAdapter.ts` 改读真实协议字段，允许同一句多次临时更新与最终定稿，忽略空文本、重复临时帧、重复最终帧与过期句子的帧，新连接重置去重状态；`src/renderer/hooks/useMonitorState.ts` 改为同一句临时字幕替换原行、定稿只移除对应句子临时行。
- **验证**：`npm test` 85/85 通过（含 5 项新增回归）；`npm run typecheck` / `npm run build` 通过；真实 Electron 冒烟（`scripts/smoke-asr-transcript.js`）通过；真实腾讯云联调：10.815 秒已知中文语音、归一化 RMS 0.0737793，19 次临时结果、3 条最终结果，SQLite 落库 3 条、界面显示一致。

### INC-02 ASR 连接生命周期缺陷（2026-10-14）

- **现象**：8 类触发条件下的可复现问题，见下表。
- **根因与修复**：
  1. 握手阶段服务端直接关闭连接——尚未 open 的 close 分支直接 return，后续重试不再安排。改为关闭后仍按退避重试，握手加 10 秒超时。
  2. 停止时连接仍在握手 / 旧连接迟到事件——向未打开的连接发结束帧；旧 close 清掉新 ws；旧 message 串入新连接；停止定时器未清除。改为握手中直接终止、按 socket 归属隔离事件、关闭成功即清除定时器。
  3. 点暂停或结束时音频尚在 500ms 队列或不足 200ms 一包——句尾音频未发送即结束。重采样器加尾部 flush，按实时速率发送队列与余量后再发结束帧。
  4. 暂停久恢复或 ASR 重连——音频切片时间未重置，服务端新连接字幕从 0 开始，影响排序与分析窗口。恢复时重置切片时钟，把连接时间映射到首个实际发送音频包的会话时间。
  5. 系统声音监听后暂停、继续——doResume 无条件调麦克风采集，实际音源被切换。改为按会话音源恢复。
  6. 连续点开始或开始被拒——重复采集、失败后音频轨道继续跑。改为同时只允许一个采集操作、开始失败释放轨道。
  7. 断线时临时字幕残留 / ASR 报错——非 connected 状态清理临时字幕，同步错误状态，重连成功清除旧错误。
  8. 旧会话 LLM 请求未结束即开始新会话——迟到结果用可变 sessionId 写入新会话，污染新会话摘要与 UI。分析任务固定原会话 ID。
- **附带修复**：临时字幕文字变化行数不变不触发自动滚动；LLM 调用失败却发 success 状态。
- **验证**：新增 `tests/asr-lifecycle.test.ts`、`tests/asr-session-boundaries.test.ts` 共 9 项回归；修复前首次边界测试复现 7 个失败，修复后全通过；完整 `npm test` 94/94；`npm run typecheck` / `npm run build` / `git diff --check` 通过；新增 `scripts/smoke-capture-session.js`（本地模拟媒体流，不访问用户设备）验证采集会话操作。
- **状态**：已修复。

### INC-03 better-sqlite3 ABI 乒乓：npm test 切 ABI 的连锁故障（2026-10-14，全组性阻塞）

- **现象**：三条互相咬合的故障——
  1. 本机 Node v24.21.0（ABI 137），better-sqlite3 二进制是 Electron ABI 130，`npm test` 的 pretest 守卫判定不匹配并尝试重建，**改写二进制**；
  2. 重建被正在运行的 electron 进程占用打出 `EBUSY resource busy or locked`，重建失败，pretest 直接退出 1，**测试根本跑不起来**（表现为 34 个「红灯」，实际是环境红灯不是代码红灯）；
  3. 手动 `npm run abi:node` 把二进制切成 Node ABI 后，若 `.forge-meta` 没清理，`electron-builder` 的 `alreadyBuiltByRebuild()` 误判「已重建过」而跳过，**把 Node ABI 的二进制打进安装包，应用一启动就崩**。
- **根因**：better-sqlite3 单个二进制文件只能对应一个运行时（Node ABI 或 Electron ABI），而「跑测试用 Node、跑应用/打包用 Electron」这两个需求天然冲突，切换是有状态、可失败的共享可变状态。
- **修复（2026-10-14 21:00 由盯播负责人确定，全组统一）**：不再跑 `npm test`，改用 Electron 内置 Node 跑 vitest——
  ```powershell
  $env:ELECTRON_RUN_AS_NODE = "1"
  & "D:\ai盯播工具\app\node_modules\electron\dist\electron.exe" "D:\ai盯播工具\app\node_modules\vitest\vitest.mjs" run
  ```
  Electron 内置 Node 是 v20 / modules 130，与二进制当前状态（Electron ABI 130）天然匹配，**不切 ABI、不碰二进制、不需要先杀进程**，同时保持打包所需的 ABI 状态。
- **验证**：2026-10-14 21:11 用新命令实测 12 个测试文件 94/94 通过、1.63 秒。作为对照，同日 21:07 用 `npm run typecheck`（不涉及原生模块）0 错误。
- **历史备注**：`scripts/ensure-sqlite-abi.js` 的 pretest 守卫原本是为解决「打包后忘切回 ABI」的事故而加的自动化，后来反因其自动重建与本机 Node 版本漂移成了新的阻塞源——**自动切换共享可变状态，在环境不匹配时会从保护机制变成故障源**。`abi:node` / `abi:electron` 手动命令与 README 相关章节保留为兜底。
- **状态**：已修复（全组改用 electron-node 跑测试）。`package.json` 的 pretest 守卫仍未移除，仍会把误用 `npm test` 的人挡在 EBUSY 上，建议后续直接删掉该钩子。
- **出处**：盯播负责人 2026-10-14 21:00 统一通知；`scripts/ensure-sqlite-abi.js`；`README.md` better-sqlite3 ABI 注意事项节。

- **现象**：`npm test` 需 Node ABI 二进制，Electron 运行/打包需 Electron ABI 二进制；本机 Node v24.21.0 / ABI 137，既有二进制为 Node ABI 127、Electron ABI 130，测试会失败或应用启动即崩。
- **根因**：单一二进制无法对应两个运行时；`build/Release/.forge-meta` 过期记录会让 electron-builder 误判已重建而跳过。
- **修复**：`scripts/ensure-sqlite-abi.js` pretest 守卫——跑测试前自动检测并切换，顺带清理 `.forge-meta`；`package.json` 提供 `abi:node` / `abi:electron` 手动切换；README 写明手动命令。
- **验证**：本机多次成功切换并完成测试与打包。
- **状态**：已修复，仍有手工依赖（换机需重跑一次）。
