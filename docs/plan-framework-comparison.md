# 话术框架「比对」设计：从覆盖率到一致性

- 作者：盯播接管
- 时间：2026-10-16
- 基线 HEAD：`407c01d`
- 状态：**设计稿**（未实现）

---

## 0. 要解决的问题

领导原话：「每1分钟对过去5分钟主播讲解的内容进行分析，**和给定的话术框架进行比对**，找出问题。」

现状做的是**覆盖率**：话术框架 → 步骤 → 靠关键词猜阶段 → 算「哪几步讲了/没讲」。

`docs/known-limitations.md` §3b.6 自认：
> 两者仍是「命中即返回、数组顺序定胜负」。后果：同句里多个阶段词命中时，优先级高者赢，另一个不出现。漏说关键词的阶段不会出现在覆盖统计里。

**覆盖率回答的是「讲了没讲」；「比对」要回答的是「说的和框架写的一不一致」。**

这两件事的证据强度完全不同：

| | 覆盖率 | 一致性比对 |
|---|---|---|
| 例子 | 「促单环节没讲」 | 「框架写保温12小时，主播说保温24小时」 |
| 判定依据 | 关键词命中（**猜**） | 数值/事实冲突（**可验证**） |
| 证据强度 | 弱，依赖关键词表 | 强，可逐字溯源 |
| 误报风险 | 高（漏说同义词就误判） | 低（数字对不上就是对不上） |

**所以「比对」应该优先做确定性可判定的部分，而不是又一个靠猜的指标。**

---

## 1. 根因：`productFacts` 是一坨自由文本

`src/shared/contracts.ts:134` → `productFacts: string`

`src/renderer/pages/FrameworkPage.tsx:137-143` 是一个多行 `textarea`，
`placeholder` 建议「每行一条」，但**没有任何结构约束**：

```
304不锈钢内胆
实验室恒温测试12小时（25℃环境）
```

`src/main/analysis/llmClient.ts:114` → `verifiedProductFacts: input.productFacts` —— 原样进 prompt。

**没有结构 ⇒ 没法做确定性比对。** 这是「比对」做不了的直接原因。

> 附带实证：`ruleEngine.ts:142` 的 `RuleEngineInput.productFacts` 字段
> **`matchRules()` 函数体内一次都没引用过**（`src/` 全树 grep 确认）。
> 也就是说本地规则引擎**完全没用过**商品事实，只把它当字符串转发给 LLM。

---

## 2. 设计方案：两条通道，按证据强度分流

### 2.1 通道 A：数值断言核对（本地，确定性，**优先做**）

框架里的商品事实大多是**带数字的断言**：
- 「保温 **12** 小时」
- 「容量 **500** mL」
- 「浓度 **5**%」
- 「充绒量 **90**% 白鸭绒」

主播口播里出现**同一个量纲、不同数值**时 → **冲突**，可确定性判定。

**实现要点：**

1. **事实解析**：把 `productFacts` 每行解析成 `{ subject, value, unit, raw }`
   - 例：`实验室恒温测试12小时（25℃环境）` → `{ subject: "保温时长", value: 12, unit: "小时" }`
   - 复用既有 `normalizeDigits()`（`ruleEngine.ts:96`）做中文数字折叠——**已有基建，不要重写**
2. **口播抽取**：在窗口内转写里抽取「数值 + 单位」对，单位须与事实**同量纲**
3. **冲突判定**：
   - 同量纲、数值不同 → `type: "frameworkConflict"`，`severity: "warning"`
   - quote = 转写里那一句的**逐字原文**（走既有证据门禁）
   - basis 写明：「框架声明 X，主播口播 Y」
4. **不判定的情况（宁漏勿误报）**：
   - 量纲不同（框架说小时、主播说分钟 → 先换算，换算不了就跳过）
   - 数值相同（正常复述，不报）
   - 主播在做**对比**（「比上一代多了X」）——需要上下文，本地判不了 → 交给通道 B

### 2.2 通道 B：语义一致性（LLM，需人工核查）

框架说「不承诺疗效」，主播说了「七天见效」→ 语义冲突。

- 走**既有 LLM 链路**（`llmClient.ts`），**不新开管线**
- 强制 `needsReview: true`
- prompt 里把结构化的 `productFacts` 一并给出（比现在塞一坨文本更准）

**为什么不把语义交给本地规则？** 因为语义冲突无法用正则判定，
硬做就是又一次「靠关键词猜」——那正是覆盖率现在的病。

## 3. 契约改动

```ts
// contracts.ts —— 新增，不动既有字段（productFacts: string 保留兼容）
export interface ProductFact {
  id: string;
  /** 原始文本行，逐字保留（证据要求） */
  raw: string;
  /** 解析出的量纲与数值；解析不出来时为 null（自由描述型事实） */
  assertion: { subject: string; value: number; unit: string } | null;
}

export type IssueType = ... | "frameworkConflict";   // 新增一类
```

⚠️ **兼容性约束**：`productFacts: string` 是既有契约，`FrameworkSchema` 里是 `z.string()`。
不能直接改成数组——会破坏既有框架数据与 `FrameworkPage` 编辑态。
**建议**：新增 `factAssertions?: ProductFact[]` 字段，由 `productFacts` 文本**派生**（解析在保存时做，
或每次分析时做并缓存），保持单一事实来源是那段文本。

## 4. 测试清单

**通道 A 必测（正例 + 反例）：**

| 用例 | 输入 | 期望 |
|---|---|---|
| 数值冲突 | 框架「保温12小时」+ 口播「保温24小时」 | 报 `frameworkConflict` |
| 中文数字冲突 | 框架「保温12小时」+ 口播「保温二十五小时」 | 报（走 normalizeDigits） |
| 数值一致 | 框架「保温12小时」+ 口播「保温12小时」 | **不报** |
| 量纲不同 | 框架「保温12小时」+ 口播「500毫升容量」 | **不报** |
| 单位换算 | 框架「保温12小时」+ 口播「保温720分钟」 | 报或不报需**明确决定**（建议：换算后一致则不报） |
| 无数字事实 | 框架「304不锈钢内胆」+ 任意口播 | **不报** |
| 对比语境 | 框架「容量500mL」+ 口播「比上一代多了200毫升」 | **不报**（本地判不了，走通道 B） |
| 证据门禁 | 冲突 quote 必须是转写连续子串 | 走既有 `hasValidEvidence` |

**反例必须写进测试**——这是本项目「误报摧毁信任」纪律的落地。

## 5. 与既有机制的关系

- **不影响覆盖率**：`ScriptLoopState` / `replayScriptPhases` / `computeStepCoverage` 一律不动。
- **不新增 LLM 请求**：通道 B 复用既有窗口分析调用，只在 prompt 里多给结构化事实。
- **去重**：走既有 `issueDedupeKey()`（`orchestrator.ts`），同一冲突持续出现只记一次、累加 `occurrenceCount`。
- **`ruleEngine.ts:142` 的 `productFacts` 字段**：本次终于真正用起来（传给通道 A 的解析器）。

## 6. 未定事项（需决策）

1. **事实解析放在哪一层？** 保存时派生（存库）vs 分析时派生（每次算）。
   - 倾向**分析时派生 + 会话内缓存**：避免 schema 迁移，且用户改了文本立即生效。
2. **单位换算表要多大？** 建议先只做「小时/分钟」「斤/公斤」「L/mL」这几组，
   其余量纲不换算、直接跳过（宁漏勿误报）。
3. **`frameworkConflict` 的 severity 默认值？** 建议 `warning`，因为它是「与框架不符」，
   不等于「违规」。用户可自行在框架里把它绑到某步骤。
