### 抖音直播间 URL 说明（需求边界，须写清）

原始需求方给出的抖音直播间链接形如 `https://live.douyin.com/295178185857`（示例：韩束官方旗舰店）。本工具**不解析该页面、不提取直播流地址**，采集路径是把该直播间的音频送进系统输出（浏览器播放 + 系统声音监听，或 OBS / 直播伴侣输出路由），再由工具做系统声音采集。也就是说：**任何能播放声音的直播间都支持，与本项目对接的是音频而不是平台页面。**

对应到方案第 4 节音频采集设计表第 3 行「浏览器直播间：浏览器输出到所选系统输出，再采集系统声音」。

- 抖音：浏览器打开上方链接播放，工具「监听系统声音」选系统声音即可。
  ⚠️ **注意**：Windows 下由主进程 `setDisplayMediaRequestHandler` 直接给出 loopback 源，
  **界面上没有「勾选分享音频」这个选项**（早期版本文案曾这样写，已因不准确而修正）。

（这一段同时是「系统/标签页音频内录」降级方案的默认形态——它本来就是主路线，不存在需要额外降级的分支。）

> 待确认：需求中提到「能盯所有直播间」，但目前只从用户处得到一个抖音直播间链接。快手、小红书、淘宝、视频号等平台的直播间是否在需求范围内、是否也要演示，尚未与用户确认。上述链接表中的平台行已移除，避免写成未确认的结论。

## 1. 项目目标与 MVP 边界

> 素材来源：方案第 1、2 节；四条线分工表。

桌面工具，实时盯任意直播间，流式语音识别实时转写主播讲解内容；每 1 分钟对过去 N 分钟（默认 5，可配置）内容做一次分析，与用户给定的话术框架比对，找出主播问题（语速、节奏、说话内容等）。

首周必须完成：Windows 麦克风与系统声音采集；云端真实流式 ASR、实时字幕、时间戳和断线恢复；可配置分析间隔和窗口；规则与 LLM 联合诊断，问题包含原话和时间证据；直播报告导出；Windows 安装包、README 和真实演示视频。

首周验收平台固定为 Windows，macOS 保留同一套架构。

### 2.2 测试运行方式（重要，本周踩坑结论）

`npm test` 现在通过 `scripts/test-electron-node.js`，用 Electron 内置 Node（v20 / modules 130）跑 vitest：

```powershell
# 本项目内直接用（脚本已自动设 ELECTRON_RUN_AS_NODE 并默认带 run）
npm test

# 或等价手写
$env:ELECTRON_RUN_AS_NODE = "1"
& "D:\ai盯播工具\app\node_modules\electron\dist\electron.exe" "D:\ai盯播工具\app\node_modules\vitest\vitest.mjs" run
```

- **单次 run 后退出**，不会进 watch。
- **不改写 native 二进制**：执行前后 `better_sqlite3.node` 的 SHA-256 相同，不需要在测试前后执行 `abi:node` / `abi:electron`。
- **新机器例外**：`npm install` 后若 `prebuild-install` 装成 Node ABI，需先 `npm run abi:electron` 再 `npm test`。
- **打包前不要每次 `npm run abi:electron`**：二进制已被占用时该命令本身也会失败（EBUSY）。改为只读 native 闸门（见下），闸门失败才协调重建。
- 单元测试子进程清空真实服务密钥，不会泄漏到输出。
- 历史：曾因 `npm test` 的 pretest 守卫自动重建二进制，与运行中的 electron 抢文件报 EBUSY，并污染打包产物。该钩子已由盯播负责人移除，详情见 `app/docs/runtime-integration-notes.md` 与本文第 14 节。

## 3. 技术选型与最终结论

> 素材来源：`README.md`、方案第 2/5/6 节、`docs/desktop-verification.md`、`package.json`。

| 决策项 | 最终结论 | 依据 |
|---|---|---|
| 桌面框架 | **Electron 33.4.11 + React 18 + TypeScript + Vite** | 主方案。系统声 loopback、原生模块（better-sqlite3）、NSIS 打包在 Windows 上路径最短；Tauri 的系统音频需另写 Rust 原生采集，一周内不赌 |
| 音频采集主路线 | **Chromium loopback（`getDisplayMedia` + main 侧 `setDisplayMediaRequestHandler` 返回 `audio:'loopback'`）** | `src/main/index.ts`（handler）、`src/renderer/capture/audioCapture.ts`。Windows 无需装虚拟声卡，见 `docs/audio-link-verification.md` §12 |
| 不做的路线 | **不解析直播间页面、不提取直播流地址**（无 FLV/m3u8 抽取、无签名逆向） | 与平台页面解耦，对接的是音频；理由见本文档「抖音直播间 URL 说明」 |
| ASR | **腾讯云实时语音识别 WebSocket**（`wss://asr.cloud.tencent.com/asr/v2/<appid>`，16k_zh） | `src/main/asr/tencentSign.ts`（TC3 签名）、`src/main/asr/tencentAdapter.ts`（适配器）；选型理由见 `docs/asr-link-verification.md` §2 |
| LLM | **OpenAI 兼容 `/chat/completions`**，`base_url` / `model` 可配，结构化输出 + 本地 Zod 校验 | `src/main/analysis/llmClient.ts`、`src/shared/schemas.ts` 的 `LlmConfigSchema` |
| 存储 | **better-sqlite3（本地单个 db 文件）** | `src/main/storage/store.ts`、`migrations.ts` |
| 默认分析节拍 | **间隔 60 秒 / 窗口 300 秒**，可选 30/60/120 秒 × 3/5/10 分钟 | `src/main/analysis/orchestrator.ts`（`windowIntervalSec ?? 60`、`windowSizeSec ?? 300`）、`windowScheduler.ts`（枚举校验） |

**明确的取舍**：ASR 备选方案（讯飞、FunASR `paraformer-zh-streaming`、SenseVoice）**均未接入**，仅在方案文档中评估过，不属于本实现。

## 4. 系统架构与模块职责

> 依据：直接读 `src/` 目录（40 个文件，其中 TS/TSX 37 个）。

| 层 | 实际文件 | 职责 |
|---|---|---|
| 采集（渲染侧） | `renderer/capture/audioCapture.ts` | `getUserMedia`（麦克风）/ `getDisplayMedia`（系统声）；`ScriptProcessor(4096)`；静音 Gain 防回放；电平回调；`ended` 检测 |
| 采集（主进程侧） | `main/capture/pcm.ts`、`devices.ts` | `PcmResamplerSlicer`（48k/44.1k→16k、200ms 分包）、`BoundedPacketQueue`（10 秒上限） |
| 主进程入口 | `main/index.ts` | 创建窗口、注册 `setDisplayMediaRequestHandler`（主屏幕 + loopback）、`capture.audioChunk` 转发 |
| ASR 适配 | `main/asr/tencentSign.ts`、`tencentAdapter.ts`、`types.ts` | TC3 签名、WebSocket 生命周期、临时/稳态分离、重连与 `gapDetected` |

## 5. 音频采集（主路线与降级）

> 本节只写采集侧。ASR 服务侧见 §6。主素材：`docs/audio-link-verification.md`。

### 5.1 主路线：Windows 系统声 loopback —— **已实测通过**

- 链路（`audio-link-verification.md` §1.1）：按钮 → `getDisplayMedia({video:true, audio:{...}})` → main 的 `setDisplayMediaRequestHandler` → `desktopCapturer.getSources({types:["screen"]})` + `audio:'loopback'` → 渲染进程 `ScriptProcessor(4096)` + 静音 Gain → `sendAudioChunk` → 主进程重采样/分包/入队。
- 实测帧特征（321 chunk / 27.3 秒 / 48kHz）：`allZeroMeanChunks=0`、`fullyZeroChunks=0`、`totalNan=0`、`totalClip=0`，**不是「±1 LSB 假非零」**。
- **Windows 不需要装任何虚拟声卡**（`audio-link-verification.md` §12）。
- 音频路由如实披露：本机默认输出为 `CABLE Input (VB-CABLE)`，测试音经过一跳虚拟线缆（§11）；这不影响电平/时间戳/落库正确性。

### 5.2 用户手势门槛（交付态硬要求）

`main` 的 handler 校验 `request.userGesture`。实测（§2）：CDP 合成点击、Win32 `mouse_event`、键盘 Tab+Enter **都不产生 user activation**，只有真实用户点击（或显式 `userGesture:true` 的 `Runtime.evaluate`）能通过。

- 验收旁路 `AILIVE_ACCEPTANCE_NO_GESTURE_CAPTURE=1` **默认关闭**，仅本地验收实例开启。
- **交付态必须真实用户点击**；使用旁路的验收结论必须标注。

### 5.3 PCM 重采样与有界队列 —— 通过（并修 2 个缺陷）

- 重采样：`floor(input.length/ratio)`，60 秒漂移 < 0.2%（无累积漂移）；曾有两个历史 bug（升采样补零致时钟快 2.76~3 倍、成包丢残余）已修并由单测锁住。
- 队列：`BoundedPacketQueue` 与 `orchestrator.pendingPackets` 均为 10 秒上限，**丢最旧而非阻塞**。本轮修：单包超上限直接拒绝入队（旧实现会让上限失效）、溢出改 `while` 连续丢。

### 5.4 无声与设备健康

- 无声告警（已实测）：连续 5 秒电平低于阈值且处于监听态 → 黄色 callout；暂停时不报警。
- 设备健康三级判据（**设计已出，代码落地情况见下**）：`docs/capture-device-health-design.md` 给出 L1 `ended` / L2 `muted` / L3 设备消失 / L4 仅电平为 0 的分类。该文档明确指出「电平驱动把设备故障与真静音合并成一条提示」是缺陷。

### 5.5 降级与平台差异

| 平台 | 状态 | 说明 |
|---|---|---|
| Windows | **通过** | 主路线，无需额外安装 |
| macOS | **未实测** | 需 BlackHole 等虚拟声卡，或系统录音权限；本周不交付 |

### 5.6 本节未实测项

- 麦克风 10 分钟长测：**未实测**（优先跑通系统声；agent 无法自行发声）。短测已验证 `getUserMedia` 可取到三路真实输入设备。
- loopback track 在「默认输出切换」时的确切行为：**未实测**（设计推导，`capture-device-health-design.md` §6）。

### 7.2 关键实现

- **窗口调度**（`windowScheduler.ts`）：固定 `nextBoundary` 递增，不以完成时间重算；**单运行 + 单待处理**，满则合并到最新窗口并计跳过数（文档 §4 记录了「错误 FIFO 尝试已撤回」）。
- **查询边界**：`start_ms < window_end AND end_ms > window_start`，跨边界片段保留完整文本（§4 A3）。
- **指标**（`metrics.ts`）：`字词总量 = 汉字数 + 英文词数`；语速分别除以讲话时长与总时长**双分母**（§6）。
- **问题去重**（`deduplicate.ts`）：问题键 = `[type, stepId或null, 排序后 segmentIds]`；引文长短变化不改变问题身份（§5）。
- **证据门禁**：每条问题必须引用输入中的 `segment_id`，`quote` 必须是该片段原文连续子串；伪造引用被拒（§2 F）。
- **LlmClient**：`MAX_ANALYSIS_TIMEOUT_MS = 20000` 整轮封顶；坏 JSON 仅修复一次；预算含修复重试。

### 10.4 运行方式硬约束（踩坑结论，必须照做）

1. **PowerShell 直接跑 npm 会被脚本执行策略拦截** → 一律用 `cmd /c "npm ..."`。
2. **启动 Electron 前必须 `$env:ELECTRON_RUN_AS_NODE = $null`**（本机默认为 `1`，会让 `require('electron')` 只返回 exe 路径而不是模块）。
3. **重装依赖后必须 `npm run abi:electron`** 重建 better-sqlite3 ABI（Electron 33 要 modules 130，本机 Node 24 要 137）。
4. 跑测试用 `npm test`（electron-node，内部清空 `DSH_SECRET_*`），**不要在测试前后切 ABI**。

## 11. 打包与部署（本轮已落地）

`package.json` 的 `build` 段已改为锁定配置，`prepackage` 增加只读闸门：

- `build.npmRebuild: false`——打包过程**不**调用 @electron/rebuild，不再改写共享 native 二进制（此前 npmRebuild 会在打包时按 Electron ABI 重建，与测试/运行争抢同一文件）。
- `build.electronVersion: "33.4.11"`——显式锁定打包目标 Electron 版本，与本地校验运行时一致。
- `prepackage` = `npm run typecheck && npm run build && node scripts/verify-electron-native.js`。
- `scripts/verify-electron-native.js` 为**只读**闸门：
  - 前置检查：必须显式锁定 `build.electronVersion` 且 `npmRebuild === false`，否则直接失败并提示原因；
  - 以 `ELECTRON_RUN_AS_NODE=1` 启动 Electron 33.4.11 子进程，删除所有 `DSH_SECRET_*` 后 `require("better-sqlite3")` 真实打开内存库并查询 `sqlite_version()`；
  - 正确 runtime → 打印 `PASS Electron 33.4.11, ABI 130, win32/x64, SQLite x.y.z` 并 exit 0；版本/平台/架构不符或加载失败 → exit 1，且提示"仅校验，不修改二进制，若 ABI 不符请结束自己负责的采集并协调 `npm run abi:electron` 后重试"；
  - **执行前后二进制 SHA-256 不变**，不会因为打包而改变共享文件状态。

### 常见错误和解决办法（README 同款表格，便于交付物自查）

| 错误 | 原因 | 解决 |
|------|------|------|
| `ASR_NOT_CONFIGURED` | 未提供 ASR 环境凭证 | 设置 `DSH_SECRET_TENCENT_ASR_SECRET_ID` / `DSH_SECRET_TENCENT_ASR_SECRET_KEY` 后重启 |
| `ASR_CONNECT_FAILED` | 密钥错误 / 未开通服务 / 网络问题 | 测试连接看具体提示；确认已开通实时识别 |
| `ASR_REMOTE_*` | ASR 服务返回错误码 | 看提示信息；常见为引擎参数或配额问题 |
| `LLM_CONFIG_INVALID` | LLM 配置不完整 | 需要 Base URL、模型名与 `DSH_SECRET_LLM_API_KEY` |
| `LLM_HTTP_ERROR` | 服务商拒绝（401/429 等） | 检查 Key 有效性、额度；应用只显示状态码，防泄漏 |
| `LLM_BAD_JSON` | 模型输出不符合约定 | 已自动修复重试一次；仍失败则该窗口跳过 LLM 分析（规则分析不受影响） |
| `CAPTURE_QUEUE_OVERFLOW` | 音频发送阻塞超过 10 秒 | 检查网络；会自动丢弃最旧数据继续 |
| 麦克风权限被拒绝 | 系统隐私设置 | Windows 设置 → 隐私 → 麦克风，允许桌面应用 |
| 共享目标没有提供音频 | 共享目标无音频轨 | 重新选择有音频的共享目标 |
| [native-gate] FAIL | native ABI 与 Electron 33.4.11 不符 | 不要全局杀进程；结束自己负责的采集后协调 `npm run abi:electron` 重试 |
| 数据库无法打开 | better-sqlite3 ABI 不匹配 | 见 ABI 一节；新机器 `npm install` 后可能需要 `npm run abi:electron` |

## 14. 环境踩坑记录

素材见 `app/docs/问题清单素材.md` INC-03。定稿时并入 `incident-review.md`：

| 坑 | 现象 | 解法 | 教训 |
|---|---|---|---|
| better-sqlite3 ABI 乒乓 | Node 与 Electron ABI 冲突，`npm test` 触发重建改写二进制，被运行中的 electron 进程 EBUSY 锁住，测试跑不起来；切回 Node ABI 又会污染打包 | Electron 内置 Node 跑 vitest（`ELECTRON_RUN_AS_NODE=1`），AAR 130 天然匹配，不动二进制 | 自动切换共享可变状态，在环境不匹配时会从保护机制变成故障源 |
| electron 占用 node_modules | 多个 electron 进程加载了 `node_modules/electron`，写二进制即 EBUSY | 按命令行 `--app-path` / `ai-live-monitor` 只杀本项目进程树，不动其他 electron | 全组共用一个 node_modules，动二进制前先确认无进程占用 |
| PowerShell 禁跑 npm.ps1 | 直接 `npm` 报脚本执行策略 SecurityError | 用 `cmd /c "npm ..."` | 本机 PowerShell 脚本执行策略限制 |
| winCodeSign 符号链接权限 | electron-builder 解压 winCodeSign 报 EPERM | 开开发者模式，或 7-Zip 排除 darwin 符号链接后重试 | 换机需重新执行一次 |
