## 0. 为什么需要它

现有兜底是**电平驱动**的：连续 5 秒电平低于阈值 → 弹「已连续 5 秒没有检测到输入声音」。

这个提示**把两种完全不同的故障合并成了一条信息**：

| 真实故障 | 现有提示 | 用户应该做什么 |
|---|---|---|
| 设备被拔掉 / 被独占 / 默认输出变了 | 「没有检测到输入声音…检查麦克风是否静音、音量是否过低」 | **重新选择设备** |
| 真的没人说话 / 直播静音 | 同上 | **什么都不用做**，或检查播放源 |

结果：用户按提示去查音量、查权限、查共享目标，**但真正要做的是换个设备**。在 8 小时无人值守场景下，这意味着**故障被当成正常静音忽略掉**，直到人工发现整场没录到。

**所以缺的不是复现，是分类。** 检测成本很低：周期性读 `AudioStreamTrack.readyState` + 比对设备列表。

## 1. 检查什么

### 1.1 三级判据（从强到弱）

| 级别 | 判据 | 含义 | 可信度 |
|---|---|---|---|
| L1 | `track.readyState === "ended"` | 轨道已死，`handleCaptureEnded` 已能捕获 | 确定 |
| L2 | `track.muted === true` 持续 > N 秒 | 轨道被系统静音（设备被独占、被切走） | 高 |
| L3 | 设备列表中该 `deviceId` 消失 | 设备被拔出 / 被禁用 | 高 |
| L4 | 电平持续为 0 且 L1–L3 均正常 | **大概率是没人说话**，不是故障 | 中 |

**关键**：L1–L3 任一命中 → 判定为「设备故障」；只有 L4 命中 → 判定为「静音」。这就是要补的分类。

### 1.2 对 loopback（系统声）的特殊性

系统声采集走的是 `getDisplayMedia`，**它的 track 不对应某一个具体输入设备**——它对应的是「系统默认渲染设备的混音」。因此：

- `track.muted` / `readyState` 仍可用（L1/L2 有效）
- L3「设备消失」这一条**语义不同**：应检查「默认输出设备是否存在」，而不是「某个 deviceId 是否还在」

具体做法：`enumerateDevices()` 里 `kind === "audiooutput"` 且 `deviceId === "default"` 的条目是否还在。若默认输出设备被拔掉且没有回落设备，这条会消失。

⚠️ **本条为设计推导，未实测**。loopback track 在默认输出切换时的行为（是 muted、还是 ended、还是静默继续）本轮未验证（COM 接口不可用，无法脚本化切设备）。

### 1.3 麦克风

`getUserMedia` 明确绑定 `deviceId`，三级判据全部适用，L3 直接有效。

## 2. 多久一次

**建议 2 秒一次**，理由：

| 周期 | 评价 |
|---|---|
| 随 `onaudioprocess` 每次检查（约 93ms） | 太频繁，`enumerateDevices()` 是异步且相对重，会拖累音频线程 |
| 500ms | 可行，但对人耳可感的故障（拔线）来说没必要这么快 |
| **2s** | 与现有 5 秒无声告警匹配：2s 检测周期 × 2~3 次 = 4~6s 内可定性，**快于或持平现有告警**，不会让用户多等 |
| 10s | 太慢，用户已经看到无声告警了，10s 后才说「其实设备没了」体验割裂 |

**实现要点**：检测必须**独立于音频回调**（`setInterval` + 异步 `enumerateDevices`），不能阻塞 `onaudioprocess`。`enumerateDevices()` 不需要额外权限即可返回设备列表（label 可能为空，但 `deviceId` 与 `kind` 可用）。

## 3. 状态放哪

现有 `AudioStatus`（`src/shared/contracts.ts:175`）：

```ts
export interface AudioStatus {
  state: "idle" | "capturing" | "paused" | "error";
  source: "microphone" | "systemLoopback" | null;
  deviceId: string | null;
  level: number;
  queueOverflowCount: number;
  lastError: AppError | null;
}
```

**建议不新增字段，复用现有结构**：

- 设备故障 → `state: "error"` + `lastError: { code: "CAPTURE_DEVICE_LOST", message: "...", retryable: true }`
- 静音 → `state` 保持 `"capturing"`，**只由 UI 侧基于 `level` 显示警告**（现状不变）

这样做的理由：设备故障是**会话级状态变更**（采集已不可用），静音是**内容级现象**（采集仍正常工作）。两者混进同一字段会让 UI 难以区分。

若需要区分「设备消失」与「设备被静音」，再加一个可选字段 `deviceState: "ok" | "lost" | "muted"`，但**建议后置**——先用 `lastError.code` 区分，够用且改动小。

## 4. 与现有机制的分工

```
                       ┌─────────────────────────────┐
                       │  track.ended 事件           │
                       │  （已有 handleCaptureEnded）│
                       └──────────┬──────────────────┘
                                  │ 立即
                                  ▼
                       ┌─────────────────────────────┐
                       │ 停止采集 + 结束会话          │
                       │ + 提示「设备已失效」（已有） │
                       └─────────────────────────────┘

                       ┌─────────────────────────────┐
                       │  2s 健康检查（本文设计）     │
                       ├─────────────────────────────┤
                       │ L1 ended        ────────────┼─→ 同上游（兜底 ended 未触发的情况）
                       │ L2 muted > 6s   ────────────┼─→ CAPTURE_DEVICE_LOST
                       │ L3 设备消失     ────────────┼─→ CAPTURE_DEVICE_LOST
                       │ L4 仅电平为 0   ────────────┼─→ 不动，交给 5s 无声告警
                       └─────────────────────────────┘
```

**分工原则**：

| 机制 | 负责 | 触发条件 | 用户动作 |
|---|---|---|---|
| `handleCaptureEnded`（已有） | track 显式死亡 | `ended` 事件 | 重选设备 |
| **健康检查（新增）** | **设备状态，非电平** | muted / 设备消失 / ended 未被捕获 | 重选设备 |
| 5 秒无声告警（已有） | **内容静音** | level < 0.005 持续 5s 且设备健康 | 检查播放源 / 无需动作 |

**关键**：健康检查**不替代**无声告警，而是**给它加前置判据**——如果设备已判故障，无声告警就不该再弹（避免两条矛盾提示同时出现）。

## 5. 对 8 小时无人值守的意义

| 故障 | 现在 | 加健康检查后 |
|---|---|---|
| 设备被拔 | 5s 后提示「没有声音」，用户以为是静音 | 4s 内提示「设备已消失，请重选」 |
| 默认输出被切走 | **可能完全无感知**（track 静默失效） | 检测到 default 输出变化 / muted → 告警 |
| 直播真的静音 | 正确提示 | 不变 |
| 长时间无人应答 | 整场报废 | **至少留下明确的故障记录** |

**配合负责人第 4 点的「前置自检」**（开机前检查设备存在、默认输出合理、网络可达），形成「开机自检 → 运行期健康检查 → 故障明确告警」的完整链路。
