## 2. 验收项 A：鉴权

### 2.1 签名算法核对

对照腾讯云官方文档 [实时语音识别（WebSocket）](https://cloud.tencent.com/document/product/1093/48982) 的
「signature 签名生成」一节，逐条核对 `src/main/asr/tencentSign.ts`：

| 官方要求 | 代码实现 | 一致 |
|---|---|---|
| 请求地址 `wss://asr.cloud.tencent.com/asr/v2/<appid>?{参数}` | `path = /asr/v2/${appId}`，`wss://` 前缀 | ✅ |
| 除 signature 外所有参数按字典序排序 | `Object.keys(query).sort()` | ✅ |
| 签名原文 = host + path + 排序后 query（不含协议） | `${host}${path}?${queryStr}` | ✅ |
| SecretKey 做 HMAC-SHA1 | `createHmac("sha1", secretKey)` | ✅ |
| 结果 base64 | `.digest("base64")` | ✅ |
| signature 必须 urlencode（+ 和 = 要编码） | `encodeURIComponent(signature)` | ✅ |
| 必填：secretid / timestamp / expired / nonce / engine_model_type / voice_id / voice_format | 全部拼入 | ✅ |
| `expired > timestamp` 且差值 < 90 天 | `timestampSec + 3600`（1 小时） | ✅ |
| nonce 随机正整数，最长 10 位 | `crypto.randomInt(0, 1<<30)` | ✅ |
| 每次连接必须重新生成 voice_id | `crypto.randomUUID()` per connection | ✅ |

**关键点：本接口用的是旧版 HMAC-SHA1 签名，不是云 API 3.0 的 TC3-HMAC-SHA256。**
代码注释里记录了历史教训：早期实现成 TC3 导致任何密钥都返回 4002 鉴权失败，
而当时的签名单测只查 URL 格式没验证算法，所以这个错带病通过了全部关卡。
这次用真实密钥跑通了，算法确认无误。

### 2.2 真实连接结果

OPEN #1 handshakeMs 369     （另一次 3 分钟运行）

## 4. 验收项 C：时间戳正确性

### 4.1 单连接内单调性

腾讯云协议行为：**每个 WebSocket 连接内，`index` 从 0 起逐句递增，
`start_time` / `end_time` 从 0 起表示「该连接内已送入音频的偏移」。**
每次重连，两者都重新从 0 计数。

实测（app 内 SQLite，会话 `190ba540`，连接 `d19b7e09`）：

| source_seq | start_ms | end_ms | 文本 |
|---|---|---|---|
| 0 | 4980 | 14700 | 大家好，欢迎来到直播间。今天给大家带来一款王炸单品，这个真的是我无限回购的一款。 |
| 1 | 14800 | 26020 | 家人们，谁懂啊？这个价格我真的会谢。官方旗舰店平时都要300多，今天在我直播间直接给你打下来。 |
| 2 | 26100 | 35400 | 这款精华的核心成分是烟酰胺，浓度5%。坚持用7天，你就能看到肤色明显提亮。这个是实测数据。 |

- `end_ms` 严格递增（14700 → 26020 → 35400）✅
- `start_ms` 与上一条 `end_ms` 不重叠（14800 > 14700）✅
- `source_seq` 严格递增，无重复 ✅
- `end_ms > start_ms` 恒成立 ✅

### 4.2 重连后时间基准重建（方案第 5 节要求）

方案明确：**"重连后重新建立时间基准，不能把新连接的相对时间戳直接当直播绝对时间。"**

代码处理方式在 `src/main/analysis/orchestrator.ts`：

```ts
private sendPacket(packet: AudioPacket): Promise<void> {
  if (this.asrStatus.state === "connected" && !this.asrAudioStarted) {
    // Tencent timestamps start at zero for each connection. Anchor them to
    // the first audio packet actually sent on that connection.
    this.asrAudioStartMs = packet.startMs;
    this.asrAudioStarted = true;
  }
  return this.asr.sendPcm(packet.pcm);
}
```

即：每个连接的第一包音频送出去时，把 `asrAudioStartMs` 锚定到**该包在会话时钟里的
位置**，之后所有 `startMs/endMs` 都加上这个偏移。这样重连后新连接的相对时间戳
被映射回会话绝对时间，不会从 0 重新开始。

`tests/asr-session-boundaries.test.ts` 有一条专门测这个：
```
it("reconnected sentence timestamps refer to the session's actual audio position", ...)
// 第一包缓冲在会话时间 9000ms，final 的 startMs=100/endMs=900
// 期望落库 startMs=9100, endMs=9900
```
**已通过。**

### 4.3 parseTencentMessage 时间映射修正

原始实现用 `audio_duration` 反推片段起止：
```ts
startMs: audioDuration > 0 ? Math.max(0, audioDuration - (endMs - startMs)) : startMs,
endMs:   audioDuration > 0 ? audioDuration : endMs,
```

这是错的。腾讯云文档明确 `start_time` / `end_time` 是「当前一段话结果在整个音频流中的
起止时间」，而 `audio_duration` 是服务端累计收到的音频时长。用后者反推会把
「上一句结束时间」错当成「本句起点」，长时间直播下时间戳整体漂移。

**已修正为直接透传**：
```ts
const startMs = typeof result.start_time === "number" ? result.start_time : 0;
const endMs = typeof result.end_time === "number" ? result.end_time : 0;
```
修正后用真实连接验证，时间戳如上 §4.1 严格单调。

## 5. 验收项 D：端到端延迟（真实实测，非估算）

### 5.1 测量方法

**端到端延迟（e2eMs）** = `final 到达时刻 − (该连接第一包音频送出的会话时钟 + 服务端给的 end_time)`

即「这句话的音频说完 → 文字定稿到我手里」的墙上时间，包含服务端识别与网络传输。

**首字延迟（firstTokenLatencyMs）** = 该句第一个 partial 到达时刻 − (连接首包时钟 + 该句 start_time)

即「这句话开始说 → 屏幕先出字」的延迟，是用户实际感知的响应速度。

### 5.2 为什么必须按连接分别锚定（重要方法论）

这是本次实测最值得记住的一条，**比长跑数据更有价值**。

腾讯云协议行为：**每个 WebSocket 连接内，`index` 从 0 起逐句递增，
`start_time` / `end_time` 从 0 起表示「该连接内已送入音频的偏移」。**
每次重连，两者都重新从 0 计数。

所以延迟计算的基准必须是**「该连接第一包音频送出的会话时钟」**，不能是会话启动时刻。

#### 踩坑实录：用会话启动时刻做基准算出 54600ms

第一版压测代码把基准写成了会话启动时刻：

```js
// 错误写法
firstSentAt = null;               // 会话启动时的时钟
// ...
rec.e2e = rec.recvAt - (firstSentAt + r.end_time);
```

跑 3 分钟、中途第 90 秒主动断线重连，结果：

```
e2eMs: { mean: 54600, p50: 95844, p90: 98203, p95: 98368, max: 98368 }
```

**平均 54 秒、P50 高达 95 秒**——腾讯云不可能慢成这样。这个数字一看就是错的。

错在哪：重连后（第 90 秒起）服务端的 `end_time` 从 0 重新计数，但基准还是
会话启动时刻（0）。于是重连后每一句都算出

```
e2e = 到达时刻 − (0 + 一个从 0 开始的小数字)
   ≈ 到达时刻本身
   ≈ 90~180 秒（运行到第几分钟就是几万毫秒）
```

也就是说，**重连后所有句子的延迟都被灌成了"会话已运行的总时长"**。数字荒谬到
一眼能看出是假的，但如果不中途重连，这个 bug 会一直潜伏——单连接场景下
`firstSentAt` 恰好约等于连接首包时钟，算出来的数字"看起来正常"。

#### 正确写法

```js
// 每个连接第一包音频送出的会话时钟
const connFirstSent = {};        // key = 连接序号
// 发送时记录
if (connFirstSent[VOICE_SEQ] === undefined) connFirstSent[VOICE_SEQ] = now;
// 计算时按该句所属连接取基准
const base = connFirstSent[VOICE_SEQ];
rec.e2e = base === undefined ? null : rec.recvAt - (base + r.end_time);
```

修正后同一份数据：

```
e2eMs: { mean: 1516, p50: 1589, p90: 2635, p95: 2635, max: 2635 }
```

**同一个运行，同一个 final 集合，只是换了基准，数字从 54600ms 变成 1516ms。**

#### 给后人的检查清单

写任何"跨连接的延迟/时间戳"计算前，先问三个问题：

1. 服务端给的时间戳，基准是什么？（本例：连接内已送入音频偏移，每连接从 0 重计）
2. 我的本地基准，在重连后还有效吗？（会话启动时刻：无效）
3. 如果服务端时钟和本地时钟不同源，我减出来的到底是谁减去谁？

第 3 点尤其容易错。本报告的 e2e 减的是「本地墙上时钟减本地墙上时钟」，
其中服务端 `end_time` 已经被转换成"对应的本地墙上时钟"（通过连接首包时钟这个
桥梁）。**不是**"本地时钟减服务端时钟"——那两个时钟没有共同原点，直接相减
得到的数字没有物理意义。

#### 6.3.4 【产品风险】会话不会自动结束

**这是本次核查暴露的、比污染本身更严重的问题。**

app 的会话没有任何自动结束机制。用户关掉浏览器、忘了点结束、或进程被挂起后，
会话会一直保持 `active`：

1. **继续采系统混音** —— 把下一场直播/别的声音也录进同一会话
2. **继续送 ASR** —— 持续产生 API 调用
3. **继续计费** —— 腾讯云按音频时长计费，挂着就在烧钱
4. **跨场次污染** —— 无人值守场景下，上一场没结束就开下一场，两场数据混一起

**实测证据**：`ae6d96d7` 挂了 61 分钟仍在 `active`；`b54b7436`/`9a416211`
从 05:47 挂到核查时（622 分钟）。

**建议的防护**（负责人将在 main 侧实现）：
- **无音频超时自动结束**：连续 N 分钟无音频包/无 chunk 增长 → 自动结束会话并告警
- **按排期窗口结束**：若配置了计划结束时间，到点自动收尾
- **残留检测**：启动时检测上一进程遗留的 `active` 会话，标记为「异常结束」而非继续使用

**对模块 A 的直接影响**：无人值守的核心承诺是「点到点自动开录」，
但**自动开录必须配套自动结束**，否则一小时变五小时、一场变五场，
计费和数据分析全部失真。

> 第②级是**降糖保健品广告口播**（`2920b432` 前 124.8s），
> 长跑是**电视剧对白**（`b217299a`）。**干净带货直播样本为 0 场**（见 §6.4.1）。
>
> 因此本节的「真实直播片段特征」应理解为**「电视类连续语音内容」**的特征，
> **不能直接外推到带货直播**——带货直播有商品展示、观众互动、BGM 段等不同形态。
> 待有干净带货素材后应重新统计。

> **更正说明（2026-10-15）**：本报告早期版本写「300 秒窗口覆盖 5~8 条」，
> 那是拿 **60 秒长片段当常态**估算的，偏保守。按实测中位数重算是 **10~11 条**。
> 「与 TTS 差约 3 倍」这个结论不变（但样本性质见上）。

**规则引擎和 LLM 的输入密度差约 3 倍**（30 条 vs 10~11 条）。

两个成因：

1. **连续说话不停顿**：播报员/角色连续说话时 VAD 切不开，单条片段被拉长到 60 秒
   （实测最大值 60.3s / 60.5s，**接近腾讯云 VAD 的强制断句上限**）。
   TTS 每句之间天然有停顿，所以片段均匀。
2. **内容密度差异**：电视内容有片头、串场、BGM 段落，无语音处 ASR 不出稳态片段，
   所以平均间隔被拉长。

**这不是采集链路变差，是内容形态差异。**

#### 对下游的三点影响

| 影响面 | 说明 |
|---|---|
| 分析窗口默认值 | 当前默认 300 秒窗口，电视类连续语音下覆盖 **10~11 条**片段（TTS 场景约 30 条）。 |
| LLM prompt 与成本 | 之前按 TTS 密度（约 30 条/窗口）估算输入量与成本。实际片段少但单条更长，token 总数未必少，但**结构不同**，需按实测重估。 |
| 语速指标 | 60 秒一条片段时，「字/分钟」的分母（有效讲话时长）会失真——片段内可能混有 BGM 段。 |

#### 建议

**保持 300 秒默认值不变，但在文档和设置页提示用户按内容密度调整。** 理由：

1. 300 秒窗口在电视类连续语音下覆盖 10~11 条片段，对「判断话术步骤覆盖、发现合规风险」
   这个目标来说是够的——判断缺什么步骤不需要 30 条样本。
2. 缩短窗口（如 180 秒）会让覆盖数降到 6~7 条，**更容易误判「这一步没说」**。
3. 真正的风险不是"样本少"，而是**长片段跨窗口**。需要确认
   `segmentsInWindow` 对跨窗口片段的处理（当前实现是 `start_ms < window_end AND end_ms > window_start`，
   保留完整文本并使用真实时间定位，符合方案第 7 节）。

**不改成动态自适应**的理由：动态窗口会让「同一场直播内窗口大小不一致」，
使问题去重和证据定位变复杂，收益不抵成本。

识别错误不一定来自 ASR 或采集链路。** 换用更稳定的源（官方 CDN、或用户手动播放的
抖音直播间）应能改善识别质量。

**结论**：第②级验证的是「真实在播内容 → ASR → 字幕」这条**链路**，
不是某个公开源的音质质量。

#### 6.6.1 外部音源有效性会漂移（模块 A 设计约束）

长跑前的源稳定性对比（45 秒 × 8 源）发现：

| 源 | 此前探测 | 本次复测 |
|---|---|---|
| CCTV-1 (720p) | 可播 | ✅ 0 丢帧、45.0s 完整、mean 3217 |
| CCTV-13 (720p) | 可播 | ✅ 0 丢帧、45.0s 完整、mean 2856 |
| CCTV-1 HD (1080p) | 可播 | ❌ **完全拉不出音频（0s 解码）** |
| CCTV-13 HD (1080p) | 可播 | ❌ **完全拉不出音频（0s 解码）** |

**两个此前测出"可播"的 1080p 源，间隔约 10 分钟后已完全失效。**

**设计约束（负责人采纳）**：

> 公开直播源的有效性会随时间漂移（本次实测中两个此前可播的 1080p 源已完全失效）。
> **任何外部音源、音频设备、网络都不是稳定前提，无人值守场景必须在每次启动前
> 做前置自检，而不是等出错才报错。**

**对模块 A 的含义**：客户点到点自动开录，如果音源失效了没人知道，那一整场就白录了。
所以「开录前自检」不是可选优化，是无人值守成立的前提条件。

**自检应覆盖**：
1. 音源可拉流（不是 404/403/超时）
2. 音源有真实音频（解码出的 PCM 非静音，而非只有空轨）
3. 采集设备存在且未被独占（参考 `audioCapture.ts` 的轨道 `ended` 监听）
4. ASR 连接可用（不是「已配置」就算，要能握手）

本次实测用的检测方法（可复用）：`probe-streams2.js` 解码 8 秒到 s16le PCM，
统计均值/峰值/非零占比。**不要用 `volumedetect` 短采样**——第一版用
`ffprobe` 查轨 + `ffmpeg -t 5 -af volumedetect`，对直播流误报大量 `NO_SAMPLES`
（音频轨明明存在，5 秒内却拿不到统计）。

#### 6.6.2 「静默失效」——无人值守最危险的失败模式

**定义**：采集轨道还活着（`track.readyState === "live"`、`ended` 事件没触发、
UI 显示「采集中」），但**音频数据不再产生**。音量条停在 0，字幕不再更新，
而所有状态指示都显示正常。

**为什么最危险**：其他失败模式都会"报错"——设备拔出触发 `ended`、源失效报 404、
ASR 断线报错误码。**只有静默失效不报错**，它让应用显示"一切正常"地录一场空。

**判据（音频采集提供，已验证）**：

| 现象 | chunks 计数 | 判断 |
|---|---|---|
| 内容静默（BGM 段落、主播停顿） | **仍在增长** | 正常，不是故障 |
| 静默失效（轨道死但状态正常） | **停止增长** | **故障** |

配套用法：如果 chunks 停止增长，再看 `capture.status` 的 chip 是否仍显示「采集中」——
若 chip 正常但 chunks 停增，即确认为静默失效。

**实测对照**：音频采集的 5 分钟常驻 stream 验证中，尾段（262s 后）`mean` 掉到
0.00001，但 chunks 仍在稳定增长（3669 个 chunk **全部非零**，zero=0）——
这是 TTS 播完进入静音段的**正常内容静默**，不是故障。

**状态**：本报告的长跑**未观察到**该模式。但静默失效是概率事件，
**未观察到不等于不存在**——防护应主动设计（采集侧加「N 秒无 onaudioprocess 回调」判据），
而不是依赖测试碰巧触发。

#### 6.6.3 【实测发现·根因已查明】音频轨道 ended 导致会话结束，脚本未察觉

**发现时间**：2026-10-15 00:12~00:18，长跑（CCTV-1）期间。

**现象**：长跑日志显示 ASR 连接在第 122 秒起为 `closed`，
此后再无 partial/final，但脚本继续发送音频包直到被停止。

```
t=61s:  asr=connected  finals=1  partials=85
t=122s: asr=closed     finals=3  partials=107
t=183s: asr=closed     finals=3  partials=107
t=244s: asr=closed     finals=3  partials=107   ← 脚本空转
```

**数据库事实**（只读核查，`myrun-9555` 库）：

```
session f941151f
started_at_iso = 2026-10-14T16:12:44.119Z   (00:12:44 本地)
ended_at_iso   = 2026-10-14T16:14:06.451Z   (00:14:06 本地)
status         = stopped
speech_intervals 覆盖 0 ~ 81.8s，会话时长 82s
```

**关键：音频与会话同步结束（81.8s vs 82s），会话是被正常结束的
（`status=stopped` 且有 `ended_at`），不是异常断开。**

**代码机制（已确认，非缺陷）**：

`tencentAdapter.ts` 的 close 分支：
```ts
this.emit("status", {
  state: this.shouldRun ? "reconnecting" : "closed",
  gapDetected: true,
});
```
`state=closed` **只可能**在 `shouldRun===false` 时出现——这是**设计意图**：
用户主动结束/暂停时不该重连（否则会像历史事故那样「暂停 2 分钟收到 4008 +
满屏重连警告」，循环浪费配额）。代码注释明确记录了这个决策。

**真正的缺陷在脚本侧**：`longrun.js` 在会话被外部结束后**没有察觉**，
继续对已停止的会话发送音频包，空转约 2 分钟。

**根因已查明（代码路径验证）**：**音频轨道自己 `ended` 了。**

两条代码事实（负责人独立核实）：

1. `audioCapture.ts:316` — `t.addEventListener("ended", () => { if (!stopped.value) onEnded(); })`
2. `MonitorPage.tsx:199` — `handleCaptureEnded()` 里 `await mon.stopSession()`
   → **写 `stopped` + `ended_at`**
3. 而 `handleDeviceLost()`（`MonitorPage.tsx:186`）走 `mon.pauseSession()`
   → **只写 `paused`**，不写 `ended_at`

数据库里是 `stopped` + 有 `ended_at`，**所以走的必然是 `track ended` 路径**。
加上音频采集确认 `handleDeviceLost` 一次都没被调用过——链条闭合。

**结论：00:14:06 音频轨道真的死了，`handleCaptureEnded` 正确捕获并结束了会话。**

**这是真故障，且兜底有效**——界面没有假装还在采，这正是该路径的设计目的。
不是误判，也不是操作人干预。

**已知事实与判定表**：

| 项 | 结论 |
|---|---|
| 已知 | 会话在 82 秒被**正常结束**（`status=stopped`、`ended_at=16:14:06.451Z`） |
| **根因** | **音频轨道 `ended` → `handleCaptureEnded` → `stopSession()`（代码路径已验证）** |
| 已排除：操作人强制停止 | ❌ 负责人的停止指令是 00:15、强制停 PID 是 00:17:33，均在 00:14:06 之后 |
| 已排除：适配器 bug | ❌ `closed` 是 `shouldRun===false` 的正确表现，设计如此 |
| 已排除：健康检查触发 pause | ❌ `handleDeviceLost` 走 `pauseSession()`，只写 `paused`；且从未被调用 |
| 已排除：脚本收尾断言 | ❌ 断言在**结束后**才点「结束」按钮，不在运行中触发 |

**真正的缺陷在脚本侧**：`longrun.js` 在会话被外部结束后**没有察觉**，
继续对已停止的会话发送音频包，空转约 2 分钟。

**修复（已实施）**：
`longrun.js` 的采样循环检测会话状态（无「结束」/「继续」按钮 → 已结束），
发现后立即停止空转，而不是等到预设时长结束。

**顺带产出的产品结论**：这次证明「音频轨道 `ended` 事件」这条兜底路径
**在真实故障下确实有效**——它正确地把一次轨道死亡转成了「会话结束 + 状态可见」，
而不是让界面继续假装在录。这与 §6.6.2 的「静默失效」形成对照：
`ended` 会报错，静默失效不会。

> **方法教训（写给后人，也写给本报告的编写者）**：
> 初版分析只看到 `asr=closed` 就推断出一条完整因果链
> （「健康检查误判 → handleDeviceLost → pause → 无自动恢复」），
> **但那是错的**。核对数据库后发现会话是**正常结束**（`stopped` + `ended_at`），
> 与推断的链路完全不符。
>
> **正确顺序：看到现象（`asr=closed`）→ 先核对最直接的事实
> （数据库里的会话状态与 `ended_at`）→ 再推断因果。**
> 不要从现象直接跳到因果链。

#### 6.6.4 【额度纪律】试用额度下的验证约束

2026-10-15 00:16 负责人传达用户指令：**当前是语音识别试用模型，额度有限**。

由此确立的验证纪律（全组适用）：

1. **禁止任何长跑**（30 分钟、10 分钟都不行）
2. **每次 ASR 验证限制在 60~90 秒内**，够验证功能即可
3. **优先复用已有数据**：库里已有 20+ 个验证过的会话，能只读分析就不新采
4. **绝不留残留会话**——这是最大的额度浪费

**第 4 条是本报告实测支持的**：残留会话 `b54b7436` 挂了 **622 分钟**、
`ae6d96d7` 挂了 **61 分钟仍在产出**。按腾讯云 ~3.2 元/音频小时计，
622 分钟 ≈ 10.4 小时 ≈ **33 元**——**单这一个残留会话的浪费，
比禁止 30 分钟长跑（约 6.4 元）省下的多 5 倍。**

**结论：额度保护的第一优先级是实现「无音频超时自动结束」，而不是限制单次测试时长。**

**实测对照**：音频采集的 5 分钟常驻 stream 验证中，尾段（262s 后）`mean` 掉到
0.00001，但 chunks 仍在稳定增长（3669 个 chunk **全部非零**，zero=0）——
这是 TTS 播完进入静音段的**正常内容静默**，不是故障。

**长跑中的观测**：本报告 30 分钟长跑同时记录 `finals` 计数、ASR 状态和
`capture.status`，可交叉判断是否出现静默失效。

**对模块 A 的建议**：在采集中增加一个「N 秒内无任何音频 chunk」的看门狗。
当前代码有 `SILENCE_WARN_MS` 的静默提示（UI 黄色提示），但那基于**电平**判断；
静默失效时电平恒 0 也会触发它，所以提示能覆盖——**但提示不等于处置**。
无人值守场景需要的是自动重连采集或明确告警，而不是界面上一条可能没人看的黄字。

### 6.7 时间锚定在 60 秒长片段下仍然正确（已验证）

**问题**：`asrAudioStartMs` 锚定逻辑会不会受长片段影响？60 秒片段跨了 300 个
200ms 包，锚定是否仍正确？

**结论：不受影响，已验证。**

锚定逻辑与片段长度无关：

```ts
private sendPacket(packet: AudioPacket): Promise<void> {
  if (this.asrStatus.state === "connected" && !this.asrAudioStarted) {
    this.asrAudioStartMs = packet.startMs;   // 只在「连接内第一包音频」时锚定一次
    this.asrAudioStarted = true;
  }
  return this.asr.sendPcm(packet.pcm);
}
```

锚点发生在**连接内第一包音频送出的那一刻**，之后 `asrAudioStarted` 置 true 就不再改动。
片段是 10 秒还是 60 秒，对锚点没有任何影响——**锚点是常量偏移，不是按片段累加的量**。

**实测验证**（用 `created_at` 墙上时间对照 `end_ms` 会话相对时间）：

| source_seq | start_ms | end_ms | 片段时长 | created_at 相对 | 误差 |
|---|---|---|---|---|---|
| 0 | 0 | 24480 | 24.5s | 25066 | 586 |
| 1 | 24480 | 53940 | 29.5s | 54696 | 756 |
| 2 | 53940 | 114240 | **60.3s** | 115009 | 769 |
| 3 | 114240 | 124780 | 10.5s | 125442 | 662 |
| 4 | 173940 | 175880 | 1.9s | 176650 | 770 |

误差 586~770ms 稳定，**没有随片段长度增长**。60.3 秒的 seq=2 误差 769ms，
10.5 秒的 seq=3 误差 662ms，同量级。这个误差就是「音频说完 → 服务端定稿 → 传回 → 落库」
的正常处理延迟，与 §5 的端到端延迟数据一致。

如果锚定存在累积漂移，长片段的误差会显著放大——实测没有发生。

**辅助证据**：`speech_intervals` 654 条，**每条间隔恰好 200ms**，覆盖 217.2 秒。
这证明时间轴粒度是精确的 200ms 包级，长片段在库里的时间跨度连续、无压缩或跳变。

## 7. 验收项 E：中间结果与稳态结果区分

### 7.1 协议层

腾讯云 `slice_type`：0=一段话开始识别，1=识别中（非稳态，还可能变），2=识别结束（稳态，不再变）。

`parseTencentMessage` 的判定：
```ts
type: sliceType === 2 ? "final" : "partial",
```

### 7.2 去重与升级逻辑

`handleMessage` 的处理（注释已说明 Tencent 的 index 标识的是"一句话"而非"一帧"，
同一句的多个 partial 和 final 共享同一个 index）：

```ts
if (seq < this.lastSeqSeen || seq <= this.lastFinalSeq) return;
this.lastSeqSeen = seq;
if (parsed.type === "final") {
  this.lastFinalSeq = seq;
  this.lastPartialKey = null;
  this.emit("final", {...});
} else {
  const key = JSON.stringify([seq, parsed.text, parsed.startMs, parsed.endMs]);
  if (key === this.lastPartialKey) return;
  this.lastPartialKey = key;
  this.emit("partial", {...});
}
```

- 允许同一句的多次 partial 修订（文本变化就发）
- 拒绝完全相同的重复 partial 帧
- 拒绝已定稿句子的迟到更新（`seq <= lastFinalSeq`）
- 拒绝旧句帧（`seq < lastSeqSeen`）
- partial → final 升级正常

`tests/asr.test.ts` 有 5 条专门测这个，全过：
- "同一句多次更新后仍接收最终字幕，后续句子正常输出"
- "重复帧、已定稿句子的更新和旧句帧不重复输出"
- "空结果与握手/结束控制帧不产生空字幕，也不阻挡该句后续结果"
- "没有临时结果时也能直接接收最终字幕"

### 7.3 落库行为（orchestrator）

```ts
private handlePartial(p: AsrPartialPayload) { ... this.emit("transcript.partial", {...}); }
private handleFinal(p: AsrFinalPayload) {
  const seg = {...};
  const inserted = this.store.insertSegment(seg);   // 只有 final 进 SQLite
  ...
}
```

- **partial 只 emit IPC 事件给 UI，不写库** ✅
- **final 才 `insertSegment` 写 `transcript_segments`** ✅
- 实测印证：3 分钟运行收到 269 个 partial、18 个 final；app 内 SQLite 只存 3 条
  （该会话只跑了约 35 秒），UI「实时字幕」区明确标注「临时字幕为识别中间结果
  （灰色斜体），不落库；稳态字幕为已定稿内容。」

### 7.4 UI 计数与 SQLite 计数差异说明

第①级里 UI 显示「稳态片段数 5」，SQLite 里该会话只有 3 条。原因：UI 计数来自
IPC `transcript.final` 事件数（含 app 停止前最后 flush 出来的、以及查询时点的差异），
SQLite 是最终落库结果。**文本内容逐字一致**（见 §10），差异是计数时机不是数据丢失。

// ws.on("close") 分支
this.emit("status", {

// scheduleReconnect()

| Node 下 `getaddrinfo EAI_AGAIN asr.cloud.tencent.com` | 多网卡且仅 WLAN 在线，Node 的 DNS 查询失败 | PowerShell 的 `Resolve-DnsName` 正常；压测脚本改用 TLS socket 预连 + `createConnection` 绕开 |
| `ws` 覆盖 `dns.lookup` 报 `Invalid IP address: undefined` | `ws` 内部按 `(hostname, options, callback)` 调用，覆盖时签名不匹配 | 放弃覆盖 DNS，改用 `tls.connect({host, port, servername})` 预连 + `createConnection` 传 socket |
| `ffmpeg -f dshow audio="CABLE Input"` 报 `Requested output format 'dshow' is not known` | 这个 ffmpeg build 只有 dshow demuxer（采集）没有 muxer（播放） | 播放改用 `ffplay`，靠系统默认输出设备 |
| PowerShell `-File` 跑含中文路径的脚本，路径变乱码 | PowerShell 按 ANSI 代码页解析命令行 | 脚本内避免中文字面量路径，或用 `[scriptblock]::Create` 时以 UTF8 读文件 |
| `param()` 块在 `[scriptblock]::Create` 下解析失败 | PowerShell 5.1 兼容性 | 改用 `$args` 传参 |
| 本机无法脚本化切换默认播放设备 | 无 AudioDeviceCmdlets 模块、无 nircmd，注册表 Sound Mapper 键不存在 | 不切设备，直接用系统当前默认输出（本机是 CABLE Input，声音经 VB-CABLE 内部路由被 loopback 采回） |
| CDP `Input.dispatchMouseEvent` 合成点击 vs `Runtime.evaluate` 带 `userGesture` | 合成鼠标事件在部分环境下不被 Chromium 认成用户手势 | 实测本例中 `Input.dispatchMouseEvent`（真实 mousePressed/mouseReleased）可以，getDisplayMedia 正常拿到 `System audio` 音轨 |
