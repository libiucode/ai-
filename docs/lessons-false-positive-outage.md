| 谁 | 编出的根因 | 错在哪 |

```sql

-- status = stopped,  ended_at_iso = 2026-10-14T16:14:06.451Z
```

**这一条就排除了「误判」假设**——因为我的链路走的是 `pauseSession()`，它只会产生 `paused`，不可能产生 `stopped`。

## 3. 真相

会话 `f941151f` 是**正常结束**的：`track` 的 `ended` 事件触发 `handleCaptureEnded()` → `mon.stopSession()` → `status=stopped`。

也就是说：**loopback 轨道在 82 秒时真的死亡了**，而现有的 `handleCaptureEnded` **正确地捕获并结束了会话**——这是它的设计目的，行为正确。

**所以本次没有发生「误判导致真实中断」。** 但「误判」的隐患是真实存在的，见 §5。

## 4. 规律（组内纪律建议）

> **误判导致的真实中断，比漏判更严重。**

漏判的后果是「本该报的没报」，用户还能从别处发现异常。误判的后果是「正常的被掐断」——**系统主动破坏了正在正常工作的流程**，而且用户往往不知道为什么。

配套的两条要求：

1. **判据正确性不能只测「该不该触发」，必须验证「正常场景下会不会误触发」。**
2. **故障路径必须留可观测痕迹**，否则事后无法归因。
   （本次能查清全靠 `status` 这个旁证；如果走的是 `paused` 路径，将完全查不出。）

## 5. 由本次复盘修掉的两个真实缺陷

### 5.1 `stalled` 判据基础不可靠（我引入）

**原实现**：`onaudioprocess` 停更 ≥ 3000ms → 判 `stalled`。

**缺陷**：
- 它假设「回调按 ~85ms 稳定节拍」——**这个假设从未被验证过**
- 实际上回调变慢只说明「没有音频要处理」，在长静默段落会正常发生
- **它和 `silent` 在语义上不可区分**——测的不是链路故障

**修法**：判据改为读 `AudioContext.state`：
- `suspended` / `interrupted` → `stalled`（浏览器明确告知音频图停止）
- `running` → 正常，**静默多久都不会判 stalled**

**验证约束（负责人要求）**：如果实测发现静默时 `ctx.state` 也异常，那就说明这个判据不该存在，删掉它。**以实测行为定，不为保留判据而保留。**

### 5.2 `stalled` 被错误地放进快速路径（我引入）

快速路径的原意是「L1/L2 不依赖设备列表，先判一次立即上报」。我加 L5 时写成了：

```ts
if (fast.state !== "ok" && fast.state !== "silent")   // ← 兜住所有非 ok 状态
```

这**把所有非 ok 状态都带了进来**，包括语义不稳的 `stalled`。

**修法**：改为显式白名单，只放语义确定的级别：

```ts
if (fast.state === "ended" || fast.state === "muted")
```

### 5.3 可观测性缺口（我引入）

**原实现**：`onDeviceLost` 只透传给 `MonitorPage`，**无 console、无记录**。

**修法**：`reportFault()` 记录 `level`（哪一级触发）+ `reason` + `lastLevel` + 时间戳 + `source` + `deviceId`。

## 6.5 工程纪律：禁止用 shell 改含中文的源码

### 现象

用 `Set-Content -Encoding utf8`（或 shell 重定向）改写含中文的 `.ts`/`.md` 文件后，**中文会变成乱码**，例如：

> 📌 **以下为引用示例，非文件损坏** —— 本节是说明「损坏长什么样」的教学材料，这些乱码字符是**故意保留**的对照样本，不是本文件（或任何文件）被损坏的证据。**请勿据此判定任何文件损坏，也不要「清理」它们。**

```
真实 → 鐪熷疄
采集 → 閲囬泦
```

### 后果

1. **源码损坏**：JS/TS 字符串里的中文被破坏后可能产生语法错误，导致整个测试文件无法解析（本项目已发生 2 次：`tests/pcm.test.ts`、`tests/capture-health.test.ts`）
2. **文档不可读**：注释和文档里的中文全成乱码
3. **误判为历史遗留**：本次复盘发现，团队在多处文件看到 `鐪熷疄` 这类乱码，**当时以为是历史遗留问题，实际就是 shell 写入导致的编码损坏**——这掩盖了真实原因

### 后果三的严重性：它和本轮的方法教训是同一个病根

「以为是历史遗留」这个标签一旦贴上，**排查就停止了**——因为人们认为「以前就有的，不是我造成的，不用管」。

这与 §4 那条方法教训（从现象直接跳到因果、跳过事实核对）**是同一个病根**：

| 场景 | 现象 | 被跳过的动作 | 后果 |
|---|---|---|---|
| 根因误判 | 看到 `asr=closed` | 核对数据库 `ended_at` | 编出错误因果链，差点掩盖真实的轨道死亡证据 |
| 乱码误判 | 看到 `鐪熷疄` | 核对文件编码历史 | 贴上「历史遗留」标签，真因（shell 编码）不被发现 |

**共同模式：现象被误读 → 归因被跳过 → 真因被掩盖。**

**规则**：改含中文的源码 / 文档，必须用 `write` / `edit` 工具，禁止 shell 重定向或 `Set-Content`。

原因：shell 的编码行为依赖当前代码页（本机为 GBK），而文件是 UTF-8。用工具写入则按 UTF-8 显式处理，不会经过代码页转换。

### 怎么判断是「文件真损坏」还是「读取端问题」（关键，别修错东西）

**看到乱码时，第一件事不是去修文件，而是先确认乱码出现在哪一端。**

| 现象 | 原因 | 正确动作 |
|---|---|---|
| 用 `read` / `edit` 工具读 → 中文正常 | **文件是好的** | **什么都不做** |
| PowerShell `Get-Content` 读 → 乱码，但 `read` 工具读正常 | **读取端按 GBK 解码 UTF-8** | **换个方式读**，绝不要「修文件」 |
| 文件被 `Set-Content` 写过 → `read` 工具读也乱码 | **文件真损坏** | 用 `write` 工具重写该文件 |

**判定方法：用 `read` 工具读。** `read` 工具按 UTF-8 解码——它读出来正常，文件就是好的；PowerShell 读出来乱码只能说明**读取方式不对**。

> ### ⛔ 强制性前置动作（不是建议）
>
> **任何「文件损坏」的判断，第一步必须是「用 `read` 工具读一次」。没做这一步，就不许下损坏结论。**
>
> 之所以升级成强制前置动作，是因为这条纪律**已经在讨论它自己的过程中失效过一次**（见下方实战误判案例）：知道规则 ≠ 执行规则，中间缺的正是一个「必须执行、不可跳过」的动作。

```powershell
# ❌ 读含中文的 UTF-8 文件时可能按 ANSI/GBK 解码，产生假乱码
Get-Content .\src\main\analysis\orchestrator.ts

# ✅ 要么用 read 工具，要么显式指定 UTF-8
[System.IO.File]::ReadAllText($path, [System.Text.Encoding]::UTF8)
```

**为什么这条必须写下来**：这条纪律的目的是「让人别用错工具」，**不是「让人去修文件」**。按假乱码去「清理」，会把一个完全正常的文件改坏——**制造一个真事故来解决一个不存在的问题**。

### 本次实战误判案例（2026-10-15，教训来自话术分析）

排查本纪律时，话术分析用 PowerShell `Get-Content` 读了 `scripts/ensure-sqlite-abi.js`，看到注释全是 `鐪熷疄` 这类乱码，据此判断「该文件是真实损坏，值得回头查」。

**该判断错误。** 盯播负责人用 `read` 工具复核，该文件前 20 行中文完全正常：

```
 * pretest 守卫：确保 better-sqlite3 原生模块与当前 Node ABI 匹配。
```

**真因**：读取端问题（PowerShell 按 GBK 解码 UTF-8），与同一轮中 JSON 报告读出的乱码**同源**。若按当时的判断去「清理」该文件，会把一个好文件改坏。

**这暴露了本纪律最讽刺的一点**：纪律本身是为了防「现象被误读」，而**在讨论这条纪律的过程中，又发生了一次一模一样的误读**——看到乱码 → 直接归因「文件坏了」→ 跳过「换个工具读一次」的核对。**§4 的病根在本纪律的元层面上又出现了一次。**

> 注：本次能定案靠的是**排他法 + 数据库的 `status` 事实**，不是靠日志痕迹（痕迹当时不存在，这正是 §5.3 要补可观测性的原因）。两者要分清：**结论可靠 ≠ 过程可追溯**。

## 8. 引用纪律（全组适用）

### 8.1 「流标签」不等于「内容性质」

流地址标签（如 `cctv13hd.m3u8`、`cctv1hd.m3u8`）**只能说明该流被标注成什么，不能说明某个时隙实际播了什么**。实测已出现标签与实际内容不符的情况。

**规则**：引用任何流地址时，不得由标签推断内容性质，必须写可观测的内容。

### 8.2 引用 `2920b432` 必须带时间区间

该会话是**三种内容拼在一场**，任何统计只有带上区间才有意义：

| 区间 | 内容 |
|---|---|
| 0 ~ 124.8s | 降糖保健品广告口播（**干净**） |
| 124.4 ~ 174.2s | **完全无音频**（前源已停、TTS 未起） |
| 174.2s 后 | 带货 TTS |

> **只写 sessionId 的引用一律视为无效引用。**

全局画像见 `evidence/session-profiles.json`。

### 8.3 样本性质必须如实标注

| 类别 | 现有样本 |
|---|---|
| 干净真实电视直播 | `b217299a`（CCTV-1 电视剧 245s）、`f941151f`（CCTV-1 82s）——**都是电视剧，不是带货** |
| 干净真实带货直播 | **0 场** |
| 广告口播 | `2920b432` 的 0~124.8s 段（**不是带货直播，但比电视剧近**） |
| TTS | 多场 |

**所以目前不得声称「已用真实带货直播验证」**——那个样本不存在。
