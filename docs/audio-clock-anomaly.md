# 实测发现：音频时间轴快于会话墙钟（未定根因，需复核）

- 时间：2026-10-15 00:5x
- 分支：`fix/real-asr-lvl1`；HEAD `0d7b9f6`
- 发现方式：只读核算 ASR 用量时，发现 `speech_intervals` 的跨度超过会话墙钟
- 脚本：`scripts/diagnose-audio-clock.cjs`（只读）

---

## 1. 现象

对全库 8 个「有音频」的会话做比值（音频时间轴 ÷ 会话墙钟）：

| 会话 | 墙钟 | 音频跨度 | 比值 | 判定 |
|---|---|---|---|---|
| `ae85dc7c` | 83s | 63s | 0.76 | 正常 |
| `190ba540` | 80s | 59s | 0.74 | 正常 |
| `e0624009` | 458s | 452s | 0.99 | 正常 |
| `a83d2607` | 158s | 158s | 1.00 | 正常 |
| `2920b432` | 901s | 742s | 0.82 | 正常 |
| `b217299a` | 261s | 245s | 0.94 | 正常 |
| **`5970a6d6`** | **326s** | **551s** | **1.69** | ★ **音频快于墙钟** |
| **`d61e4b32`** | **30s** | **38s** | **1.27** | ★ **音频快于墙钟** |

**音频时间轴比真实时间还长，这在物理上不可能**——除非「送给 ASR / 记为语音区间的音频」比真实时间跑得快。

## 2. 两个时间基不同（这是关键）

同一会话里，两类数据的时间轴来源不同：

| 数据 | 时间戳来源 | 是否受音频时钟漂移影响 |
|---|---|---|
| `speech_intervals` | `PcmResamplerSlicer` 的 `nextStartMs`（**本地按样本数累加**） | ✅ 会 |
| `transcript_segments` | 腾讯云返回的 `start_time` + 连接时的墙钟锚点 | ❌ 不受本地切片器影响 |

实测 `5970a6d6`：

| 项 | 值 |
|---|---|
| 会话墙钟 | 326s |
| `speech_intervals` | 2225 个，到 **551s** |
| `transcript_segments` | **仅 2 个**，到 **8s** |

**稳态片段只跑到 8 秒，但语音区间跑到 551 秒**——两者相差 543 秒。同一次采集，两条时间轴差了将近 3 倍。

## 3. 机制候选（未验证，按可能性排序）

**候选 A：渲染层音频回调成簇触发。**
`ScriptProcessor` 由 AudioContext 时钟驱动。若 loopback 轨道曾短暂饥饿、随后一次性送出积压缓冲，回调会在很短的墙钟内连续触发多次，每次推 4096 样本。切片器忠实按样本数推进 `nextStartMs`，于是**音频时间轴跑在墙钟前面**。比值 1.27~1.69 与「积压后突发」的形态一致。

**候选 B：`sourceRate` 与实际数据率不匹配。**
`PcmResamplerSlicer.push` 用 `outCount = floor(input.length / (sourceRate / 16000))`。渲染层传的是 `ctx.sampleRate`。若该值大于实际数据率，`ratio` 偏大 → 输出样本偏少 → 音频钟**变慢**（与观察到的变快相反），故本候选方向不对，除非另有环节。

**候选 C：跨会话残留。**
`start()` 里 `this.slicer = new PcmResamplerSlicer()` 重建，`nextStartMs = 0`，理论上不会残留。**但若 `ingestAudio` 在会话结束到下次 `start()` 之间仍被调用**（采集比会话多活一会儿），包会被 `bufferPreStartAudio` 缓冲——上限 3 秒，不足以解释 225 秒。

**三个候选都不足以单独解释 225 秒。根因未定。**

## 4. 影响

| 影响面 | 说明 |
|---|---|
| 分析窗口 | `segmentsInWindow` 按会话相对 ms 切片。若音频钟偏快，窗口覆盖的**实际音频区间**会小于标称，导致部分时段被重复分析或漏分析 |
| 静默统计 | `longestSilenceMs`、静默分布均基于 `speech_intervals`，**偏快的时间轴会拉长算出的静默** |
| 用量核算 | 不能拿音频时间轴当计费基准（计费是 ASR 连接时长），否则高估。已在 `scripts/usage-reconcile.cjs` 里改用「墙钟为上界、音频为下界」的区间估计 |
| 报告时间轴 | 若报告用 `speech_intervals` 画问题时间轴，标称时刻会早于真实时刻 |

**本轮不据此下结论、不改代码**——两个样本都来自探针脚本驱动的会话，不能确定普通用户手动操作是否同样发生。

## 5. 下一步（需额度或零额度的复核）

1. **零额度**：核 `5970a6d6` / `d61e4b32` 的生成脚本（`probe-persist5.ps1` 系），确认当时是否有「音频来源非实时」的操作（例如音频文件被加速处理）。
2. **零额度**：加一条断言到探针脚本——每 N 秒对比「音频时间轴增量」与「墙钟增量」，比值 > 1.1 就报警。这样下次采集能当场抓到，而不是事后算出来。
3. **需额度**：一次 60~90 秒的真实采集，同时记录渲染层 `sendAudioChunk` 的调用时刻与主进程 `nextStartMs`，直接判定回调是否成簇。

**在此之前，任何用 `speech_intervals` 时间轴做的统计都要标注「可能偏快」。**
