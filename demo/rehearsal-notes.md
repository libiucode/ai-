## 四、发现的一处真实约束（演示时要注意）

### 排期结束时刻只能精确到「分钟」

脚本 §7 要求：「演示前请先在『分析设置』→『定时监听』配一个**马上要到**的结束时刻。」

核对 `SettingsPage.tsx` L310/L319：两个输入框都是 `<input type="time">`。

**这意味着**：
- `type="time"` 的默认粒度是**分钟**（`HH:mm`），**秒不可选**
- 所以「马上到点」最接近的做法是：**把结束时间设成下一分钟**
- 实际等待时间最长为 **60 秒**（若当前是 12:34:59，设 12:35 只需等 1 秒；若当前是 12:34:01，要等 59 秒）

**演示建议**：在 §7 开始前先看秒表，把结束时刻设成**下一分钟**，然后正常讲前面内容，
让它在自然节奏里到点。**不要在现场临时发现「还有 50 秒」而冷场。**

> 这一条**不影响功能正确性**，但**影响演示节奏**——属于「没彩排过就不会知道」的细节。

## 六、验证方法论：三个必须先做的检查

> 这一节不是事故记录，是**可复用的检查动作**。
> 来源：本轮桌面端做产物级验证时踩到的三个坑，以及从 `endReason` 空串 bug 归纳出的一条。
> 每条都给「违反会怎样」的反例——因为这类错误的共同点是**看起来一切正常**。

### 检查 1：测产物前，先确认产物是新的

**动作**：改完 `src/` → `npm run build` → 再跑产物探针。顺序不能省。

**反例**：改完 renderer 直接跑探针，看到「读回没生效」，差点判成功能 bug、准备动手修。
加诊断标记后确认 effect 跑到了、判据也对，只是 **asar 里还是旧代码**。`npm run build` 后立刻正常。

**一条可执行的判断**：探针结果与代码读出的预期不符时，**先 build 再重跑，别急着改代码**。

### 检查 2：探针不能改变被测状态

**动作**：探针只读。若需要「手动触发一次」做对照，**必须另起一个干净的实例做**，不能在同一实例上先读再触发。

**反例**：探针里加了一步「手动 change 一次」，想区分是 value 绑定坏还是 effect 没跑。
但它触发了 `onSelectDevice` → `setDeviceFallbackNotice(null)`，**把要验的回落提示清掉了**，
于是一度以为「提示没显示」是 bug。实际提示一直是好的。

**本质是观测者效应**：探针看起来「只是在读状态」，实际上写入了。这类错误极难自查。

### 检查 3：断言要按契约写，不要按实现写

**动作**：写完单测问一次——「这个输入有没有第二种形态？」

**反例（本轮最贵的一个）**：`formatEndReason` 第一版用 `reason ?? "unknown"`，
单测测的是「null → 未记录」和「undefined → 未记录」，全过。
但 `??` **只兜 null/undefined，空串会漏过去**——界面显示成「结束方式：」后面一片空白。
这个 bug **单测永远发现不了**，因为断言是按「我对实现的理解」写的，压根没想到空串这个输入。
最后是**产物级探针**逐个试取值时才暴露的。

**根本原因**：单测的断言来自我对实现的**理解**，而理解有盲区。所以「我没想到的输入」单测测不到。

**对照表**（按契约写 = 多测右边这一列）：

| 按实现写断言（不够） | 按契约写断言（要补） |
|---|---|
| 测「null 返回 unknown」 | 测「**空串**也返回 unknown」 |
| 测「`??` 的行为」 | 测「`||` 才兜得住的**所有**输入」 |
| 测「对象有值」 | 测「对象为 `undefined` / 字段缺失」 |
| 测「列表有数据」 | 测「**列表为空**」（空列表常走另一条分支） |
| 测「id 存在」 | 测「id 已消失」+「设备列表为空」两种边界 |

**这三个检查有一个共同点**：违反它们时，现象都是「看起来正常」——代码看着对、测试全绿、
探针也跑通了。所以必须在写之前就做，不能等出问题再补。
